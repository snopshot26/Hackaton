# DatsSol — практическая пошаговая стратегия

Этот документ собирает ключевые решения для стабильной игры в DatsSol и переводит правила в прикладной план на ход/раунд.

## 1) Что важнее всего в первые 120 ходов

1. **Не теряйте ЦУ любой ценой.**
   Потеря ЦУ = мгновенный вайп всех плантаций + штраф по очкам.
2. **Стройте связную сеть от ЦУ.**
   Любая отрезанная плантация не даёт очков с терраформации и начинает деградировать.
3. **Не спамьте команды через одну и ту же выходную точку.**
   Каждая следующая команда через тот же узел теряет эффективность.
4. **Приоритет по апгрейдам:**
   - `repair_power` (универсально усиливает ремонт/стройку),
   - `signal_range` (оперативная глубина сети),
   - `settlement_limit` (масштаб),
   - защитные апгрейды по ситуации (`earthquake_mitigation`, `beaver_damage_mitigation`).

## 2) Базовая макро-логика на весь раунд

- Игра идёт по 600 ходов, поэтому планируйте в 3 фазы:
  - **Фаза A (0–180):** экспансия и постановка «каркаса» сети.
  - **Фаза B (181–420):** удержание темпа очков, точечные диверсии, контроль рисков.
  - **Фаза C (421–600):** конвертация в итоговые очки раунда, минимизация потерь.

- На каждой фазе держите минимум:
  - 60–70% действий в экономику (стройка/ремонт/связность);
  - 20–30% в контроль угроз (бобры/катаклизмы/починка узлов);
  - 10–20% в PvP (диверсии только там, где есть шанс добивания).

## 3) Микро: как принимать решение каждый ход

Используйте этот порядок:

1. **Проверка выживания:**
   - не под угрозой ли ЦУ;
   - не рвётся ли связность цепочки;
   - нет ли критично просевших HP у ключевых узлов.
2. **Проверка катаклизмов по `meteoForecasts`:**
   - землетрясение (`turnsUntil = 0`) — заранее избегайте «HP на грани»;
   - формирующаяся/движущаяся буря — убирайте наиболее ценные/уязвимые узлы с траектории, если можете.
3. **Распределение строительных маршрутов:**
   - не перегружайте одну выходную плантацию;
   - разводите команды по нескольким выходным точкам.
4. **Ремонт до безопасного порога HP:**
   - особенно узлы-мосты, через которые идёт связность.
5. **Агрессия только после экономики:**
   - диверсия в цель, которую можно добить в ближайшие 1–2 хода;
   - либо добивание логова бобров, если дэмэдж гарантированно ваш.

## 4) Стройка без самоубийства по лимиту

- Если выходите за лимит плантаций, удалится самая старая — можно случайно потерять ЦУ/опорный узел.
- Перед массовой стройкой:
  1. посчитайте текущий `settlement_limit`;
  2. проверьте, какая плантация самая старая и критична ли она для цепи;
  3. при риске сначала купите `settlement_limit`, потом расширяйтесь.

## 5) Где брать максимум очков

1. **Стабильная терраформация > хаотичная агрессия.**
2. **Клетки с X и Y кратными 7** приоритетнее для долгого удержания (больше очков за % прогресса).
3. **Добивание вражеской плантации** выгодно, только если реально забирать last-hit.
4. **Логово бобров** очень выгодно (x10 от клетки), но имеет смысл бить его только при высокой вероятности финального урона.

## 6) Ротация ЦУ

Переносите ЦУ только если это даёт явный плюс:
- сокращение длины критичных маршрутов;
- восстановление/усиление связности;
- уход от явной точки давления соперника.

Перенос «ради эксперимента» в темповой фазе чаще вредит.

## 7) Минимальный шаблон бота

Каждый ход бот должен делать:

1. `GET /api/arena`.
2. Сформировать приоритеты: survival → economy → control → pvp.
3. Отправить `POST /api/command` **не пустым** телом:
   - хотя бы 1 полезное действие (`command`, `plantationUpgrade` или `relocateMain`).
4. Логировать ошибки и события (`GET /api/logs` периодически).

## 8) Частые ошибки

- Пустой запрос команд (получаете `empty command...`).
- Потеря связности и «молчаливая» потеря очков с изолированных плантаций.
- Перегрузка одной выходной точки (падение эффективности почти в ноль).
- Игнор прогноза катаклизмов на несколько ходов вперёд.
- Стройка выше лимита без контроля, какая плантация будет удалена.

## 9) Короткий чеклист на ход

- [ ] ЦУ в безопасности?
- [ ] Нет критичных разрывов сети?
- [ ] Учтён `meteoForecasts`?
- [ ] Команды распределены по разным выходным точкам?
- [ ] Есть хотя бы одно полезное действие в `POST /api/command`?
